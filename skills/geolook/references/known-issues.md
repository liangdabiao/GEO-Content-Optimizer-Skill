# 已知坑与实测教训

> 每次跑真实项目踩出来的坑。遇到「不对劲但说不清为什么」的现象，先来这里对表。

## 1. 豆包（302.AI 模式）单题可能卡 3 分钟

**现象**：采样时豆包个别题 `ReadTimeout`，一题拖 3 分钟，看起来像死循环。

**根因（已修复）**：302.AI 模式下豆包走 `search_then_ask()`，这里曾**硬编码 timeout=60**，
且 `_ask_chat()` 超时重试 2 次（delays=(1,3)），每题失败 ≈ 188s；更坑的是 `ask()` 传进来的
`timeout` 参数**被吞掉**（不影响豆包）。

**现在**：`ask()` 把 timeout 转给 `search_then_ask()`，缺省读 `AI302AI_SEARCH_ASK_TIMEOUT`
（默认 45s）。改这里不用动代码。

**运维口诀**：
- 想调豆包单题超时 → 设 `.env` 的 `AI302AI_SEARCH_ASK_TIMEOUT`，别设太大。
- 某个平台持续超时 → 先查是不是硬编码参数，再决定要不要无限重试。**别让任务空转**。

## 2. 302 国内端点 vs 海外端点，模型 ID 不一样

**现象**：用旧模型 ID 调 `api.302.ai` 返回 500/503/403，容易误判「账号不支持 gemini/claude/perplexity」。

**事实**：
- **国内端点 `https://api.302ai.cn`**（新版本目录）才是本账号可用目录，代码 `AI302AI_BASE` 已是它。
- 海外 `api.302.ai` 与国内目录**模型 ID 不同**，不能拿海外目录的 ID 在国内端点用。

**规则**：判断「某平台/某模型是否可用」前，先 `GET https://api.302ai.cn/v1/models`
拉全量列表，用真实请求逐个验证，再下结论。结论与预期不一致，先和用户讨论再动手改配置。

## 3. SPA 空壳页（国内官网最常见的 GEO 致命伤）

**现象**：抓取器对某些页面只取到 0 词（Vue/React 静态壳，正文全靠 JS 渲染），
有时访问返回的是**错误壳页**（如 mi.com 商品页返回 `err.www.mi.com/04.html`，3149 字节）。

**处理**：
- 体检看 `word_count` 接近 0 的页，直接按 P0「纯前端渲染，AI 抓取器读不到」进工单。
- 别拿这类页面的"抓取成功"当"内容可取"——先手工 GET 一眼确认是真实正文还是错误壳。

## 4. llms.txt 重要页面会混进超范围页面

**现象**：`generate` 默认按体检分数取 top-12 页写入 llms.txt「重要页面」，
品牌口径只聚焦某个品类时，超范围页面（如只做手机，混进行李箱/电视页）会漏进去。

**处理**：`geo.json` 的 `brand` 里配 `llms_include_urls` / `llms_exclude_urls`（URL 子串列表），
generate 会先过滤再取 top-12。例：

```json
"brand": { "...": "...", "llms_exclude_urls": ["suitcase", "tvspeaker"] }
```

## 5. 采样指标的口径红线（别自创）

- **国内 ≠ 海外**：跨市场平均提及率无解释力，报告各占一张表。
- **API ≠ 网页端、Web ≠ App**：信源系统性不同，单独记单独算。
- 没有答案原文/截图/采样环境记录的，不许标「真实采样」。
- 采样频率克制，不批量滥采、不模拟登录。

## 6. 耗时异常优先查代码，别无限等

任务卡住/异常慢时，先定位是不是：硬编码超时 → 重试次数乘数 → 无进展的死循环。
确认是参数问题就**停止重试、如实记录缺失样本**，别让用户干等。
